# Cloudflare D1 — virtualrow's server-side persistence

This document is the operational reference for virtualrow's server-side
persistence, which lives on [Cloudflare D1](https://developers.cloudflare.com/d1/)
(SQLite accessed from a Cloudflare Worker binding). See issue #670 for the
rationale and the design decisions (D1–D5).

## TL;DR

- Two databases on the Cloudflare account on the free tier:
  - `virtualrow-prod` — `af8509b2-a7ac-4115-9cbe-347b70de611c`
  - `virtualrow-dev` — `96eb755a-7d8c-4205-9d72-48cdcc9fd743`
- One Cloudflare Worker — [`workers/api/`](../workers/api/) — bound to the
  right DB per environment. The binding name is `DB` in both envs so Worker
  code never branches.
- Migrations live at repo-root [`db/migrations/`](../db/migrations/) and are
  managed by `wrangler d1 migrations`.
- GitHub Actions workflow
  [`.github/workflows/d1.yml`](../.github/workflows/d1.yml) applies migrations
  + deploys + curls `/health/db` on PR, on merge to `main`, and weekly.
- **No Cloudflare-API secret is ever loaded into the client bundle.** The
  `npm run build` output is GitHub-Pages-safe (#670 FR4 / NFR3).

## The Cloudflare dashboard

<https://dash.cloudflare.com/> — **D1 → Databases** lists `virtualrow-prod`
and `virtualrow-dev`; **Workers & Pages** lists `virtualrow-api` and
`virtualrow-api-dev`. Audit activity on the API token is under
**Manage Account → Audit Log** (#670 NFR5).

## DB and binding model (D2)

| Environment    | Worker name          | D1 database        | Binding |
|----------------|----------------------|--------------------|---------|
| `dev`          | `virtualrow-api-dev` | `virtualrow-dev`   | `DB`    |
| `production`   | `virtualrow-api`     | `virtualrow-prod`  | `DB`    |

Binding IDs are in [`workers/api/wrangler.toml`](../workers/api/wrangler.toml).
IDs are **not secrets** — they are safe to commit and to appear in CI logs.

## Migrations workflow (D3)

Tool: the **built-in** `wrangler d1 migrations`. Files live at
`db/migrations/NNNN_<description>.sql` and apply in order. Wrangler records
the applied-migration list in a `d1_migrations` table it manages itself.

### Create a new migration

```bash
npm run db:create-migration -- <short_description>
# e.g. npm run db:create-migration -- add_workout_sessions
```

Wrangler creates `db/migrations/NNNN_<description>.sql` with `NNNN`
auto-incremented. Edit the SQL by hand — the file ships empty.

### Apply locally

```bash
npm run db:migrate            # applies against the local SQLite file
                               # under .wrangler/state/v3/d1/ (gitignored)
```

### Apply to the remote `virtualrow-dev`

```bash
npm run db:migrate:remote      # applies against the remote virtualrow-dev DB
```

Requires a `CLOUDFLARE_API_TOKEN` scoped to `virtualrow-dev` (see below).

### Production migrations are CI-only

Production migrations are **never** applied from a developer laptop. The
`d1` workflow applies them on push to `main` against `virtualrow-prod`.

### "Rollback" is a forward-only reversing migration

D1 does not have Flyway-style `undo_NNNN.sql` scripts. To reverse a bad
migration, write the next-numbered migration that undoes it
(`0002_undo_foo.sql`) and apply it forward. Destructive reversals
(dropping a column that production code still reads) must be staged across
releases: ship the code change that stops using the column first, then the
drop in a later PR.

## Local dev flow (D4)

`wrangler dev --local` uses a local SQLite file under
`.wrangler/state/v3/d1/`, which is gitignored. No shared dev DB; every
contributor has their own local DB. **Nobody needs a Cloudflare account to
build the client.**

```bash
# From the repo root:
npm run dev                    # SvelteKit dev server (unchanged)

# From workers/api/:
cd workers/api
npm install
npm run dev                    # wrangler dev --local, serves at :8787
```

### Reset the local DB

```bash
rm -rf .wrangler/state/v3/d1
npm run db:migrate
```

### Without a Worker

With no `CLOUDFLARE_*` env vars set and `workers/api/` not running, the
client works exactly as today (localStorage only; #670 FR8). The Worker is
optional for local work on client features that do not touch persistence.

## Deployment

Both envs deploy from CI only:

- **PR touching `db/migrations/**` or `workers/api/**`:** migrations apply
  `--remote` against `virtualrow-dev`, then `wrangler deploy --env dev`,
  then `curl $URL/health/db` and assert `{"ok":true}`.
- **Push to `main` on the same paths:** same against `virtualrow-prod` and
  the production Worker.

The workflow guards on `CLOUDFLARE_API_TOKEN` + `CLOUDFLARE_ACCOUNT_ID`
being set; it fails fast with a clear error if they are missing.

## Secrets and rotation

### Which workflow uses which secret

| Workflow                           | Secrets used                                      |
|------------------------------------|---------------------------------------------------|
| `.github/workflows/d1.yml`         | `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`   |

No other workflow in this repo reads a Cloudflare secret. The client build
(`.github/workflows/deploy-pages.yml`) receives only
`VITE_INTERVALS_CLIENT_ID` — see FR4 below for the enforcement.

### Token scope (D5 / NFR1 / AC10)

`CLOUDFLARE_API_TOKEN` is scoped to **only**:

- **D1:Edit** on `virtualrow-prod` and `virtualrow-dev`.
- **Workers Scripts:Edit** on `virtualrow-api` and `virtualrow-api-dev`.
- **Account:Read** (minimum needed to resolve the Workers subdomain for
  the healthcheck URL).

**It is not account-wide.** Verify in the Cloudflare dashboard under
**My Profile → API Tokens** before merging any PR that uses it.

### Rotate the Cloudflare API token

1. In the Cloudflare dashboard → **My Profile → API Tokens**, click
   **Create Token** and use the scope above.
2. Copy the new token value immediately — Cloudflare shows it once.
3. In GitHub → **Settings → Secrets and variables → Actions**, update
   `CLOUDFLARE_API_TOKEN` to the new value.
4. In the Cloudflare dashboard, **delete** the old token (not just roll).
5. On the next CI run (push an empty commit to a branch, or trigger
   `workflow_dispatch` on `d1`), confirm the workflow passes.

No code change is required to rotate (NFR2). The DB IDs in
`wrangler.toml` are **not** secrets and do not need rotation.

## No credentials in the client bundle (FR4 / NFR3)

- `vite.config.ts` reads only `VITE_*` env vars; `CLOUDFLARE_*` is not a
  `VITE_*` prefix, so Vite will not surface it.
- Verified at build time:

  ```bash
  npm run build && grep -R -E "d1|wrangler|$CLOUDFLARE_ACCOUNT_ID" dist/ && \
    echo FAIL || echo OK
  ```

  Expected: `OK` (grep finds nothing).

The client never talks to D1 directly; it talks to the Worker, which holds
the binding.

## Secret scanning / push protection (AC9)

Enable GitHub's native secret scanning + push protection for
`MaximumTrainer/virtualrow` under
**Settings → Code security → Secret scanning / Push protection**. This is
a repo-admin setting and must be verified manually before merging a PR
that introduces or rotates any CI secret.

Steps:

1. Open **Settings → Code security** on
   <https://github.com/MaximumTrainer/virtualrow/settings/security_analysis>.
2. Turn on **Secret scanning**.
3. Turn on **Push protection**.

If the setting is inaccessible to the current admin, record that fact in
the PR description and verify in the next admin session.

## Troubleshooting

- **"Resource not accessible by integration"** on the workflow's Cloudflare
  calls: the API token is missing or has the wrong scopes. Check
  `CLOUDFLARE_API_TOKEN` and rotate per above.
- **`wrangler dev --local` cannot find `wrangler.toml`:** run from
  `workers/api/`, not the repo root.
- **`npm run db:migrate` says "No migrations to apply" unexpectedly:**
  wrangler is looking at the wrong `migrations_dir`. Check the
  `migrations_dir = "../../db/migrations"` line in `workers/api/wrangler.toml`.
- **`/health/db` returns 500:** the Worker reached D1 but `SELECT 1` did
  not return `{ok: 1}`. Inspect the Worker logs with
  `npx wrangler tail --env <dev|production>` from `workers/api/`.

## Telemetry shipping (#421)

With `VITE_API_BASE_URL` set, the app ships its scene telemetry log to
`POST /api/telemetry` every 30 s and on `pagehide` (by `sendBeacon`). It is
anonymous (a random run id per page load plus the build SHA), and it is off
whenever the rower has turned crash reports off. Periodic `sample` events
are thinned to the latest one per batch. The Worker's caps, scrubbing and
retention are described in `workers/api/README.md`.
